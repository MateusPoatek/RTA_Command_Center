Epic Games GCP Architecture

The production design for the Epic Games account (El Salvador, Philippines, Bulgaria) on Google Cloud. It is the next step after the POC described in the RTA Board Engineering Guide. For the engineering and delivery teams.

At a glance

  • One tenant (Epic) with three site profiles in one manifest. One container image, no code forks, hosted on Telus Digital GCP and deployed with Terraform.
  • The POC logic that runs in the browser or on a laptop moves to Cloud Run services and jobs. The alert rules run once, on the server, so the board, Google Chat and reports all show the same result.
  • Team Leads get alerts as direct messages from a Google Chat app, with an "On it" button that calls back. A server-side "already posted" log replaces the POC's 30-minute age heuristic.
  • Identity comes from Google Workspace through IAP. The system handles workforce data only. It never touches Epic player or customer data.
  • Tenancy Pattern B (shared project) is recommended but still under assessment. Region, WFM-network connectivity and the PH and BG clock APIs are open decisions (section 11).

1. Scope and summary

This page designs the production system for all three Epic Games sites. The POC is described in the RTA Board Engineering Guide. Read that first. It runs on a laptop: a local API, a Vite app, a Chrome extension, and a browser-side scheduler and Chat loop.

Each site has a different data profile today.

SiteSources todayStatus
El SalvadorVerint and GTTlive in POC
PhilippinesVerint only. The clock system API is being negotiated.pending access
BulgariaClock system is Verint MyTime. API access is being negotiated. Not yet in Verint capture.pending access

Same image, one manifest. The three sites run the same container image. Differences live in one tenant manifest for Epic, with one site profile per site (section 8). This follows the rule of one image plus one manifest per client.

Every service name below is a Google Cloud product. Each is explained in a few words the first time it appears. Anything not yet decided is marked "proposed" or "open".

Out of scope here. Any AI or agent layer is covered in the companion page Epic Games Agentic Layer. This page is the deterministic core only.

Build versus extend

The company already runs a production WFM automation platform on Telus Digital GCP: an Automation Anywhere orchestrator with about 125 bots, PostgreSQL without PII, and Intelligent Insights for audit and observability. The decision is to extend it, not rebuild. This design adds only three things: real-time Verint capture, the RTA board with one-click human approval, and the GTT and Verint reconciliation. Logs and metrics are exported to Intelligent Insights.

5. Alert sequence

From capture to Team Lead acknowledgement, with escalation. All timing runs on the server. Today's POC escalates from TL to Ops Manager after 5 minutes, then to the WFM Director 10 minutes later. These timings are the POC's and carry over unless the rules change.

  participant V as Verint capture
  participant I as Ingest
  participant R as Rules engine
  participant L as Posted log (Cloud SQL)
  participant T as Cloud Tasks
  participant C as Chat app
  participant TL as Team Lead
  participant OM as Ops Manager
  V->>I: capture (tenant and site tagged)
  I->>R: normalised and joined data
  R->>R: evaluate alert rules, severity
  R->>L: has this alert and level been posted?
  L-->>R: no
  R->>T: enqueue Sev 1 alert for the TL
  T->>C: deliver (retry on failure)
  C->>TL: direct message with card
  C->>L: record posted
  alt TL presses On it
    TL->>C: button callback
    C->>R: acknowledge (who, when, reason)
    R->>L: store ack, stop escalation timer
  else no acknowledgement in time
    R->>T: enqueue next level
    T->>C: deliver
    C->>OM: direct message with card
    C->>L: record posted at new level
  end

6. Data and PII

The system handles workforce data only. That means schedules, activity states, clock events and supervisor assignments for Epic agents. It never reads or stores Epic player or customer data.

Operational rows follow a retention rule still to be set.Role-based: TL sees own team, RTA and Ops Manager see their scope, WFM sees all in tenant

AggregateKPI history, shrinkage, scorecard feedBigQueryKept for history and evalsWFM, dashboards in Looker Studio
SecretsVerint token, GTT credential, Chat app settingsSecret ManagerRotated per policyService accounts only
  • Raw capture payloads are dropped after normalisation. Only the normalised fields are kept.
  • Tokenisation. Names and employee IDs are tokenised before any LLM call. De-tokenisation happens at the UI edge. See the companion agentic page.
  • Frameworks. Baseline is SOC 2 Type II controls. Employee data falls under PIPEDA and GDPR. It is not PCI data.
  • Extension relay. Sending Verint capture from a browser to a backend moves PII off the RTA's machine. That needs a deliberate decision before it is turned on.

7. Security and identity

Roles through IAP

IAP puts a Google sign-in in front of the board API and the Chat callback. Roles map to Google Workspace groups. Identity must resolve to the Telus corporate Workspace domain.

RoleWorkspace group (proposed)Sees
TLOne group per tenantMy team screen, own people only
RTAOne group per tenantFloor screen, all TLs of the tenant
Ops ManagerOne group per tenantFloor and escalations, reports
WFMOne group per tenantAll screens including Details, reports, dashboards

A TL's own team comes from the GTT supervisor column. Verint has no TL field. The mapping from a signed-in user to a supervisor name is an open item.

8. Tenancy and the three sites

Recommended: Pattern B, a shared GCP project with tenant_id routing, row-level security and per-tenant service accounts. Status: under assessment. Epic is a non-bank client, so it falls in the "permissive" group that may run on Telus Digital GCP. The POC already runs on a shared-project model. See GCP tenancy models (POC_Redefined/Product_and_Architecture_docs/gcp-tenancy-models.html).

What would trigger Pattern A (a dedicated project for Epic):

  • Epic or Telus legal asks for regulated-data isolation or a contract term that requires it.
  • A data-residency requirement that the shared project's region cannot meet.
  • An audit finding on shared infrastructure for this tenant.
  • Epic data of a more sensitive class than workforce data enters scope.

Isolation choice follows regulatory exposure, never the Gold, Silver or Bronze tier.

One tenant, three site profiles

One tenant, Epic. One manifest. One profile per site. The Verint organisation follows the pattern BPO_Client_Site_LOB.

SiteTimezoneVerintClock systemStatusWhat the manifest carries

Adding a source later means editing the manifest, not the code. Alerts that need a clock source (for example "not clocked in") stay off for a site until its clock source is connected. That behaviour is proposed.

10. Operations

Service levels

These are targets, proposed for agreement. They are not measured yet.

ObjectiveTargetMeasured from
Alert latencyAt most 2 minutesVerint capture time to the Chat message sent
Chat deliveryDelivered with retries. Failures after retries are logged and alarmed.Dispatch task result
Shift reportReady by end of shiftSchedule time to file written
GTT freshnessAt most 10 minutes oldLast good poll to now

Monitoring and alerting

  • Cloud Logging and Cloud Monitoring (logs and metrics) for every service and job, with one dashboard per tenant.
  • Alert policies on each objective above: latency, dispatch failures, report not written, GTT stale.
  • Telemetry exported to Intelligent Insights for audit and observability.
  • Retries are required. The GTT report service and the Chat endpoint both fail in a transient way, such as auth rejections and 5xx errors. The POC already retries both. Production keeps retries and treats a single failure as normal, not an incident.
  • Runbooks for: GTT stale, Chat delivery failing, Verint capture silent, report job failed.
